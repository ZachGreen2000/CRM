# Project Coding and Design Conventions\n\nThis document outlines the established patterns and conventions observed across the repository, ensuring consistency and maintainability.\n\n## 1. Architectural Conventions\n\n*   **Separation of Concerns (High):** The system enforces strict separation between *what* needs to be done (Agent), *how* to talk to the LLM (Provider), and *what* actions are available (Tool).\n*   **Factory Pattern Usage:** Service instantiation (especially LLM Providers) must utilize the Factory pattern (`src/Settings/provider_factory.py`) to ensure modularity and easy swapping of underlying services.\n*   **Agent Specialization:** Agents are designed to be highly specialized (e.g., `email_agent`, `task_agent`), rather than general-purpose scripts.\n\n## 2. Data & State Management Conventions\n\n*   **Hybrid Persistence:** Data is not stored in one place. Factual, structured data resides in the **Relational DB** (`src/Database/`), while transient, semantic knowledge resides in the **Vector Store** (`src/Memory/`).\n*   **Context Compression:** Raw conversation history must *never* be passed repeatedly. The `thread_summarizer.py` mechanism must be used to condense context before passing it to the LLM.\n*   **Schema Definition:** Database structure must be defined declaratively using SQL files (`.sql`) before application code interacts with the schema.\n\n## 3. Naming Conventions\n*   **Agents:** Follow the pattern `[Capability]Agent` (e.g., `client_agent.py`).\n*   **Modules:** Core functional areas are grouped into dedicated packages (`src/Orchestrator/`, `src/Memory/`).\n\n## 4. Execution Flow Convention\n*   The primary execution flow is always mediated by the **Orchestrator** (`src/Orchestrator/brain.py`), which coordinates the interaction between the Agent, Memory, and Providers."
